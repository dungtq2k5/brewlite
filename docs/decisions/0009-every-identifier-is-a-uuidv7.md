# 0009 — Every identifier is a UUIDv7; the order number people read is a separate sequence

**Status:** Accepted · **Date:** 2026-09-24 · **Supersedes:** — · **Superseded by:** —

## Context

Ids are created in four services and by clients (the idempotency key), and some rows are written with raw SQL. Auto-increment ids leak volume, collide across databases and need a round trip to exist. Random UUIDv4 scatter inserts across the B-tree and give no order for cursor pagination.

At the counter, though, people need something they can read and say aloud — the wireframe shows *Mã đơn: #1042*. A UUID cannot be called out across a shop.

## Decision

- **Every id is a UUIDv7**, generated by the application: Prisma `@default(uuid(7))`, or `newId()` from `@brewlite/contracts`. No database default, no v4, no cuid.
- "Every" includes non-key UUID columns and ids clients create — **`Idempotency-Key` is a UUIDv7** too.
- Every id accepted from outside (path, query, body, header, event payload) is parsed as a v7; anything else is `400 VALIDATION_FAILED` and is never looked up.
- The human-facing **order number** is `orders.order_no`, a `BIGINT` from a Postgres sequence, shown as `#1042`. It is unique, never reused, never used as a key in an API path, and never derived from the id.
- Ids from Stripe (`cs_…`, `pi_…`, `evt_…`) are opaque strings, never UUID columns.

## Consequences

- Inserts append to the index; `ORDER BY id` is creation order, which cursor pagination uses without a tiebreaker.
- A client can create the idempotency key offline before the request, with the same helper the server uses.
- **Cost:** a raw `INSERT` must supply `newId()`; forgetting it fails `NOT NULL`, which is the good outcome.
- **Cost:** order numbers are global and grow forever; they reveal roughly how many orders the shop has taken. Accepted for one store.
- **Cost:** the order number sequence has gaps after a rolled-back insert; nobody may treat it as a count.
